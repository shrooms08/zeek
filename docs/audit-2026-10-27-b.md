### R1. Critical: one crafted transaction halts the engine and all three keyholders

- **Found by:** the Rust reviewer and the security auditor, independently.
- **Where:**
  - `crates/zeek-engine/src/decrypt.rs:237-244`: a compact-block hit that
    doesn't decrypt in the full transaction becomes a fatal
    `MalformedTransaction`;
  - `crates/zeek-engine/src/chain.rs:394-395`: `decrypt_full(...)?` inside
    ingest;
  - `crates/zeek-keyholder/src/follower.rs:66`: the same `chain::ingest`;
  - also `crates/zeek-engine/src/audit.rs:350-354` and
    `crates/zeek-verify/src/checks.rs:436-439`.
- **Why it can be forced:**
  - Compact trial decryption reads only the first 52 bytes of the ciphertext,
    with no authentication tag. Full decryption checks the whole ciphertext.
  - Consensus doesn't check that a non-coinbase output decrypts. Whether NU7
    adds such a rule isn't confirmed; that is the main uncertainty.
  - So anyone can pay the public vault address with an output whose
    ciphertext is valid for 52 bytes and corrupt after them.
- **What happens:**
  - Every ingest pass fails on that block, for ever.
  - The board freezes: no round closes, settles, pays or refunds.
  - The keyholders freeze the same way.
  - `/v1/health` keeps saying ok; only `/v1/status` (stored tip vs chain tip)
    shows the stall.
  - Funds are frozen, not lost.
  - It costs one testnet fee and moderate skill.
- **The Pocket already does the right thing:** it skips such a note
  (`crates/zeek-pocket/src/wallet.rs:538-580`).
- **Fix:** treat a compact hit that doesn't fully decrypt as "not a game note"
  and skip it, in decrypt, audit and the verifier, with a test.
- **Risk:** the code change is small, but the engine, all three keyholders and
  the site's wasm verifier must ship together. If they disagree, the
  keyholders refuse to sign.
- **Recommendation:** prepare and test the patch on a branch now, and deploy it
  only if a stall appears. That is a decision for you (see below).

### R2. Critical (data), seen live: a one-block reorg deletes a fresh settlement

- **Where:**
  - `crates/zeek-engine/src/processor.rs:503` stores `settled_at_height:
    tip.height`;
  - `crates/zeek-engine/src/db.rs:1204-1217` deletes
    `settlements WHERE settled_at_height >= fork`, plus their
    `unclaimable_payouts` rows.
  - A settlement only reads blocks at least 10 below the tip, so the deletion
    is never needed. The comment saying "the confirmation policy should make
    impossible" is wrong.
- **Live (Railway logs, last 5 days, read-only):**
  - 335 reorgs at the engine;
  - "rollback discarded settled rounds" 7 times: rounds 1710 (twice), 1780,
    1820, 1843, 1931 and 1944, and 7–8 times on each keyholder.
  - All six were no-payout rounds, so they re-settled identically. The ledger
    is clean (`shortfall: 0`, `unpaid_rounds: []`).
- **When it bites:** a round that pays out in the same pass, then gets a
  one-block reorg. That round is re-settled as "awaiting signatures" while
  its payout row exists, so it is never marked paid again.
- **What happens then:**
  - The ledger counts it as owed for ever, so the status page shows a false
    "Short by X ZEC" (`apps/web/src/lib/vaultHealth.ts:28`).
  - Its unclaimable rows are lost.
  - `operator_float` is understated, which worsens F1.
  - Nothing is paid twice.
- **Odds:** about 1% of rounds are discarded and about 5% pay out, so a few
  percent per day.
- **Fix:** delete only settlements whose last block read
  (`window.end + mtp_window − 1`) is at or above the fork. Small, engine-only.
  It needs an engine redeploy, between rounds, with no payout in flight. A
  decision for you.

### R3. High: "Restore with 24 words" deletes the stored Pocket before checking anything

- **Found by:** the web reviewer and the security auditor.
- **Where:**
  - `apps/web/src/screens/WalletScreen.tsx:422-424`: `await p.forget(); await
    p.restore(...)`;
  - `packages/zeek-pocket/src/worker.ts:330-337` refuses to restore over an
    existing wallet, which is why the UI forgets first.
- **What happens:** a wrong word, a birthday like "4,500,000" (NaN), a relay
  error or a short passphrase all fail after the wallet is gone. A blank
  birthday scans from block 1, which in practice never finishes. Coins are
  safe only if the player has the correct words.
- **Fix (web-only, TS):** restore with `replace: true` in the worker.
  1. Validate the birthday.
  2. Fetch the tree state and build the core.
  3. Only then save over the old wallet.

  Drop `forget()` from the UI.

### R4. High: leaving the backup step locks the player in a loop, and the backup is never asked for again

- **Where:** `apps/web/src/screens/WalletScreen.tsx:64` (the words live only in
  the screen's local state); `apps/web/src/machines/wallet.ts:43` (status
  updates are ignored in "backup").
- **What happens:**
  - A player creates a Pocket and taps the logo or Back before checking the
    words.
  - `/wallet` then shows "Make your Pocket" again, and creating fails ("a
    wallet exists"). They are stuck until a reload.
  - After the reload nothing remembers the backup was skipped.
  - With no `navigator.storage.persist()`, Safari can evict the wallet.
- **Fix (web-only):** let status move "backup" to "unlocked" when the words
  are gone. Store a "not backed up" flag and offer "Back up now" from it.
